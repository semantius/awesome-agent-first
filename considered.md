# Considered, not listed

Every candidate assessed for this list that did not end up in the readme, why, and what would change that.

This file exists because an inclusion rule nobody can see being applied is just a claim. Nothing here is a criticism of the software. Several of these are better built and more widely used than entries that did qualify, and a few fail on something as small as a missing licence file. "Not listed yet" is meant literally: say so in an issue when one of these changes and it gets re-checked.

The criteria are in [contributing.md](contributing.md). Software that fails clause 4 by design is recorded separately in [agent-only.md](agent-only.md), because being built agent-only is a decision rather than a shortfall.

**Corrections are welcome and will be made quickly.** Every claim here was checked against the project's own repository, documentation or a live response, and is a snapshot of what was public when it was checked. That method is fallible in three ways: a capability can exist somewhere the check did not look, undocumented behaviour is invisible to it, and everything here goes stale as projects ship. If something is wrong about your project, open an issue or a pull request with a link to what shows otherwise. Factual corrections are not argued with. Judgement calls, meaning whether a clause is the right clause, are worth discussing in the open, and that discussion belongs in an issue where everyone can read it.

## Fails a clause

- [agent-desk](https://github.com/huabeitech/agent-desk) - Fails clauses 2 and 3. The MCP server it ships at `/api/mcp` registers two tools, `server_time` and `service_info`, and `internal/ai/mcps/registry.go` leaves a comment where further providers would go; the working MCP integration is the client that lets its own AI agent call external tools, which is the consumer direction rather than a way in. The dashboard's HTTP surface does reach roles, permissions, tickets and knowledge bases, but nothing documents it: the documentation site has no API reference, `llms.txt` and `.well-known/mcp.json` both return 404, and the "Open API" in the channel settings is OpenIM, a chat channel. Authorization is enforced server-side, which satisfies clause 5, but authentication is a password login issuing a session token, with no credential an agent could hold. **Would qualify with** an OpenAPI document over the dashboard routes and MCP tool providers covering tickets, conversations and knowledge.
- [Relaticle](https://github.com/relaticle/relaticle) - Fails clause 2. Custom field definitions are read-only everywhere they are reachable: the MCP server offers `list-custom-fields-tool` and `get-crm-schema-tool` with no write equivalent, `CustomFieldsController` implements only `index`, and no console command defines one. Creating a custom field requires the Filament admin panel, and defining fields is something an operator has to do, so clause 2 fails. Re-read under the operator wording: the verdict is unchanged, because no shell path exists for a reference agent to take either. **Would qualify with** a writable custom-fields endpoint or MCP tool.
- [Agentic Postgres](https://www.tigerdata.com/blog/postgres-for-agents) - Fails clause 4 under the audience test. Its human paths are psql, third-party SQL clients and the console SQL editor, which are database administration tools rather than interfaces for the people whose records live there. **Would qualify with** a shipped interface for working with the data as records.
- [Airtable](https://airtable.com) - Fails clause 2. The access half is not where it falls short. SCIM 2.0 creates, patches and deletes users and groups, `Update collaborator base permission` and `Update workspace collaborator` move a person or a group to a level narrower than full, and the permission levels themselves are a fixed set nobody extends, so that much is parity rather than a gap, though both of those writes are marked "Billing plans: Enterprise (pre-2023.08 legacy plan), Enterprise Scale" and below that tier the grant is something only the interface does. Clause 6 is met twice over, by an llms.txt tree at `airtable.com/developers/llms.txt` whose first section is addressed to agent integrations, and by RFC 9728 protected-resource metadata at `mcp.airtable.com` advertising `schema.bases:write` among its scopes. What the machine interface does not reach is the schema it holds that scope over. Fields are created at `POST /v0/meta/bases/{baseId}/tables/{tableId}/fields` and nothing deletes one, nor deletes a table, while bases, workspaces and views all have deletes. Update field "updates the name, description, and/or options of a field", so the type conversion the interface performs from a menu has no API form. Views can be read and deleted but not created, and their filters, sorts and grouping are configurable nowhere but the interface. Because that llms.txt indexes every endpoint Airtable publishes, the absences are a finding rather than an argument from silence. Re-read under the operator wording, and they survive it: retyping a field and building the view a team works in are things an operator does to run a base, not presentation settings, and below the Enterprise tier granting access is a click as well. The first-party MCP server at `mcp.airtable.com` is a real way in, creating bases, records, automation drafts and interface pages, but it does not close the schema gap. **Would qualify with** field and table deletion, field type conversion, and view creation.
- [AnyDB](https://www.anydb.com) - Fails clause 2. Business database platform whose hosted MCP server at `mcp.anydb.com` is a way in rather than a read path: 56 tools, of which `anydb_create_type` and `anydb_update_type` define types, fields, layout, title formulas and child policy and migrate existing records, while `anydb_get_type_definition` and `anydb_discover_types` read the model back and the server publishes its permission guide and a machine-readable authoring schema as MCP resources. Discovery settles clause 6 several times over: RFC 9728 protected-resource metadata naming the scopes `mcp:read`, `mcp:write` and `mcp:author`, RFC 8414 authorization-server metadata with dynamic client registration, PAR, DPoP and a revocation endpoint, and an OpenAPI document served at `/openapi/spec.yaml`. What the machine interface does not reach is the access model. `anydb_get_permissions` and `anydb_check_permissions` only read, `anydb_list_team_groups` only lists, neither the OpenAPI document nor the TypeScript SDK adds a write, and the admin documentation puts group creation behind the Manage Team panel and role assignment behind the Team Properties panel. Roles themselves are built-in for everyone, which is no gap at all, but a team group and the permissions hanging off it are things only the interface creates. Re-read under the operator wording: granting access to what it has just built is one of the three things an operator must do, so the verdict is unchanged. `anydb_create_share` does grant a group view-only access to a single record, which is narrower than full access, but a per-record share is not a role assignment. Clause 4 is comfortably met by the web app. **Would qualify with** tools that create team groups and assign roles or permissions.
- [AnythingLLM](https://anythingllm.com) - Fails clause 1. The machine half is stronger than the product's framing suggests, and none of it is where it falls short. `server/swagger/openapi.json` publishes 60 paths under the title AnythingLLM Developer API, "endpoints that enable programmatic reading, writing, and updating of your AnythingLLM instance": workspaces and threads, documents and folders, embeds, users, invites and instance preferences, with `POST /v1/workspace/{slug}/vector-search` for retrieval and `GET /v1/document/metadata-schema` returning "the known available metadata schema" and the acceptable type of each key at runtime. Roles are the fixed set of default, manager and admin, which is parity rather than a gap, and the per-resource grant the round trip weighs most heavily is reachable through `POST /v1/admin/workspaces/{workspaceSlug}/manage-users`, which sets a workspace to be accessible by the given user ids. Every admin path does carry the sentence "Methods are disabled until multi user mode is enabled via the UI", but that describes where a person does it rather than a restriction on who may: `server/utils/middleware/validatedRequest.js` calls `next()` outright while the instance is in single-user mode and `AUTH_TOKEN` or `JWT_SECRET` are unset, so on a fresh instance an agent can `POST /api/system/enable-multi-user` itself and unlock the rest, which is a bootstrap step rather than an asymmetry under [contributing.md](contributing.md#verifying-clauses-2-and-3). What it cannot do is find that endpoint, which the published document omits, the same weakness as `update-env` telling a caller to "refer to codebase" for its keys, and that is a clause 3 finding about discovery rather than a clause 2 finding about capability. Clause 1 is what rules it out. The product is the assistant: custom agent skills, agent flows, and an MCP integration that is a client reading `anythingllm_mcp_servers.json` to call external servers, which is the consumer direction rather than a way in. The workspace store underneath is the memory-store category the readme's Related Lists already serve. **Would be reconsidered if** the knowledge store became a governed way in of its own, such as a first-party MCP server over its own workspaces under the same permission model.
- [Appwrite](https://appwrite.io) - Fails clause 3. Backend platform whose machine half is otherwise among the strongest assessed here. The OpenAPI document published in `appwrite/specs` reaches all three things an operator does: `POST /tablesdb/{databaseId}/tables` creates a table with columns and indexes inline, typed endpoints under `/tables/{tableId}/columns/` add string, integer, boolean, datetime, enum, relationship and other columns, and table `permissions` with `rowSecurity` grant access to `Role.user(id)`, `Role.team(id)`, `Role.team(id, role)` or `Role.label(id)`, so an agent can create a team through `POST /teams`, give a member a role through `/teams/{teamId}/memberships`, and grant that role read on the one table it has just built. Rows have full create, update and delete with bulk operations and transactions, and `Query.search` runs full-text search over a full-text index beside granular query operators. Clause 6 is met several times over, by that OpenAPI document, an `llms.txt` addressed to agents, an MCP server card at `/.well-known/mcp/server-card.json`, and protected-resource metadata for the hosted MCP server at `mcp.appwrite.io` naming scopes such as `project:databases.write` and `project:teams.write`, and clause 7 by project API keys created through `POST /project/keys` with their own scopes and expiry. What the model does not do is describe itself. `tablesDBGetTable` and `tablesDBListColumns` return each column's key, type, size, required flag and default, but the `table` and `column` schemas carry no description property, so an agent reading a table another agent defined learns its shape and never its meaning. Clause 3 asks for names and descriptions on the entities and fields themselves, and the operation descriptions in the OpenAPI document, however thorough, describe Appwrite's API rather than the model a project has built with it. **Would qualify with** a description property on tables and columns, returned wherever their schema is read.
- [Attio](https://attio.com) - Fails clause 2. The schema half is strong, and the identity plane is the cleanest example on this page: `POST /v2/objects` creates a custom object, `POST /v2/{target}/{identifier}/attributes` adds fields across the documented attribute types with select options and statuses beside them, and SCIM 2.0 sits inside the same OAuth-scoped API rather than off to one side, with `Create a SCIM user` taking an `appRole` of `admin` or `member`, `Create a SCIM group` building the team, and `List SCIM schemas` describing both, all under `user_management:read-write`. That is the identity plane delegated the way [contributing.md](contributing.md#verifying-clauses-2-and-3) says it may be, by a product that implements the protocol itself. Clause 3 is settled by `POST /v2/objects/records/search` across objects, granular filters on the query endpoints, and attribute definitions carrying titles, types and options; clause 6 by an OpenAPI document at `api.attio.com/openapi/api`, an llms.txt indexing every documentation page as markdown, and a first-party MCP server at `mcp.attio.com/mcp` behind OAuth whose `update-list` tool changes a list's permissions. The authorization plane is where it stops. Objects carry permissions in the product: the help centre's Manage access to objects documents a Permissions tab granting the workspace, teams, individual members and automations one of full access, read and write, or read only. The `object` schema in the OpenAPI document carries `api_slug`, `singular_noun`, `plural_noun` and `created_at`, and nothing in that document reaches object permissions, so an agent that has just created a custom object cannot then say who may see it. Re-read under the operator wording, and that is the operation to name: setting who may see an object it has just defined. Everything else an operator needs is reachable. `PATCH /v2/lists/{list}` does grant on a single resource, through `workspace_access` and a `workspace_member_access` array at three levels, but its entries carry `workspace_member_id` only, so a team SCIM has just created is a grouping nothing can be granted to. Workflows, dashboards and saved views have no endpoints either, and views are listable without being creatable. Clauses 4, 5 and 7 are comfortable. **Would qualify with** object permission endpoints and team grantees on list and object access.
- [Budibase](https://budibase.com) - Fails clause 2. The model and record halves are sound: the public API documented in `packages/server/specs/openapi.json` creates, updates and deletes tables with a typed column schema, creates views, and searches rows with `string`, `fuzzy`, `range` and `equal` filters combined by `allOr`. Access is where it falls short. The only authorization write in that reference is `POST /roles/assign`, "a business/enterprise only endpoint" that places users in an existing role, and nothing in it creates a role or sets which role may read or write a table or a view. The documentation describes custom roles as created under the Data section by clicking **Manage roles**, and the builder reaches per-resource grants through `POST /api/permission/:roleId/:resourceId/:level` and roles through `POST /api/roles`, internal routes the published reference never mentions, so a caller reading what Budibase publishes cannot find them. The per-resource grant is the half that weighs most, and it has no documented machine form. API keys are generated per user in the portal, so an agent acts as a person, and no first-party MCP server was found; Budibase Agents is the consumer side. **Would qualify with** the role and resource-permission routes published in the public API reference.
- [Documenso](https://documenso.com) - Fails clause 2. The signing half is fully machine-callable: the v2 OpenAPI document at `app.documenso.com/api/v2/openapi.json` publishes 89 paths over envelopes, documents, templates, fields, recipients, attachments and folders, `envelope-find` takes a `query` search parameter alongside filters on type, template and status, and audit logs and completion certificates download per envelope. What that document does not contain is anything for organizations, teams, members, roles, webhooks or API tokens, all of which the web app has, and its thirteen tags are the whole of the surface, so an agent can create an envelope and cannot say who on the team may see it. A reference that indexes every path it serves makes the absence a finding rather than an argument from silence. Clause 6 is met by that document, and team-scoped tokens carry clause 5. **Would qualify with** organization, team and member endpoints, and webhook and token management beside them.
- [Dosu](https://dosu.dev) - Fails clause 2. Engineering knowledge base whose discovery is exemplary: an llms.txt at `dosu.dev/llms.txt` addressed to agents, a public OpenAPI document at `api.dosu.dev/openapi.json`, an `auth.md` following the WorkOS convention, RFC 9728 protected-resource metadata, OAuth with dynamic client registration, and a hosted MCP server at `api.dosu.dev/v1/mcp`, so clause 6 is met several times over. The records half is sound too: `POST /v1/deployments/{deployment_id}/pages`, `PATCH` and `DELETE /v1/pages/{page_id}`, folder creation and moves, batch archive and delete, imports from GitHub, GitLab, Notion, Confluence and Coda, and publishing back to each of them. What the OpenAPI document does not reach is the access model. Nothing creates a deployment or knowledge store, and nothing adds a member, defines a role or grants a person or team access to one. The only access operation is `POST /v1/mcp/deployments/{deployment_id}/api-keys`, which creates a key "scoped to a deployment's organization" rather than to the deployment, and the protected-resource metadata advertises `"scopes_supported": []`. An agent can therefore fill a knowledge base and cannot say who may see it. Clause 7 fails for a related reason, since keys are `sk_user_` keys created under Settings, Account, API keys and act as the person who made them. Clause 1 is mixed rather than failed: much of the product is Dosu acting as an agent, answering and triaging on GitHub and Slack, with `/ask`, chat threads and an LLM gateway in the same API, and only the knowledge store is the producer side this list is about. Clause 3 is partly met, because search runs through the MCP `read_knowledge` tool and `/ask`, the MCP tool list is visible only after authenticating, and `docs.dosu.dev` redirects into Dosu's own app rather than serving a static reference. **Would qualify with** endpoints that create deployments or knowledge stores and grant access to them, and keys narrower than an organization or issued to an agent.
- [ERPClaw](https://www.erpclaw.ai) - Fails clause 2, and clauses 5 and 7 with it. Open-source ERP covering the general ledger, order to cash, source to pay, inventory, payroll and tax, whose every operation is an action behind one entry point, `scripts/db_query.py --action {action} --args`, run as local Python against the database. It is not single-device software: the README says "SQLite by default, PostgreSQL fully supported … point it at PostgreSQL when you outgrow a single file", so a shared deployment is possible. The access model is what stops it. Users and roles exist, with `add-user`, `update-user`, `add-role`, `assign-role` and `seed-permissions` among the actions and a `company_ids` list restricting a user to particular companies, but nothing sets what a role permits beyond the seeded defaults, so a role an agent defines grants nothing it can shape. Nor does the engine enforce the grants it holds. `erpclaw_lib/rbac.py` says "RBAC is opt-in. Skills call require_permission() in actions that need enforcement", and allows every action while no user exists, and the dispatcher's only permission action is `check-telegram-permission`, which a front end asks before acting. The caller is not authenticated either, since an action receives no credential and a user id is whatever the caller passes, so any process with a shell reaches everything and an agent cannot hold a credential of its own. The README is candid about this, saying identity and authorization "are being built out alongside Atrium", its own agent loop. ERPClaw Web adds JWT sign-in and role-based access, but as a FastAPI proxy in front of the same scripts, so it governs only the callers that go through it. Clause 1 is mixed as well, because the product ships as a skill for the OpenClaw and Hermes agent runtimes and its primary interface is the assistant. **Would qualify with** authorization enforced in the dispatcher for every action, callers authenticated with credentials of their own, and an action that sets what a role permits.
- [Formbricks](https://formbricks.com) - Fails clause 2. The management API creates and updates surveys, which is the model an agent would want to define, and covers responses, action classes, webhooks and contacts. Two things stop there. Contact attribute keys, the closest thing the product has to user-defined fields, are readable and nothing creates one, since the API reference lists get-all and get-by-id with no POST beside them. And the access model has no machine form at all, with organizations, teams, project roles and workspace permissions documented as user-management screens, so an agent that has just built a survey cannot say which team may work on it. Clause 7 is weak for the same reason, because the documentation describes a personal API key that "gives you full access to all data and settings available in your Formbricks account" rather than a credential scoped to what an agent needs. **Would qualify with** endpoints for teams, project roles and contact attribute key creation.
- [Hanko](https://www.hanko.io) - Fails clauses 3 and 4 self-hosted, and clause 2 on Hanko Cloud, so no deployment passes all three. Authentication and user management server. Self-hosted, the configuration half is sound: `config.yaml` covers third-party and custom OIDC providers, SAML, passkeys, passwords, MFA, sessions, webhooks, audit logging and multi-tenancy, and an agent edits that file itself, while the admin API at `docs.hanko.io/openapi-admin.yaml` creates, updates and deletes users, emails, credentials, sessions and webhooks. There is no role or permission model to grant through, which is a fixed model rather than a gap, and the repository lists organizations, roles and permissions as in progress. Reading is thin: `GET /users` filters by id and email and sorts by creation date only, with no search over the model. And the open-source distribution ships login, registration and profile components but no administration interface, so a person running it self-hosted manages users through the same API the agent calls, which is clause 4's "reaching your own data should not require building a client first". Hanko Cloud has that console, but there providers and settings are configured in the console with no management API, and the admin API is limited to the Pro and Enterprise plans. **Would qualify with** search over users and either a shipped administration interface for self-hosting or a management API for Cloud projects.
- [Notion](https://www.notion.com) - Fails clause 2. The Developer Platform that launched on 13 May 2026 closed most of the distance: the `ntn` CLI is generally available on every plan, Workers run first-party TypeScript in Notion's own sandbox, and the hosted MCP server reaches further than the REST API does, with `notion-create-database`, `notion-update-data-source` and `notion-create-view` defining the model and `notion-query-data-sources` accepting SQL over it. Clause 3 is comfortable, since `Retrieve a data source` returns every property's name, type and description, and search comes in two forms, keyword through `notion-search` and semantic through `notion-ai-search` across Notion and connected sources. Clause 6 is met four times over, by OpenAPI documents at `/openapi.json` and `/openapi-adminApi.json`, an `llms.txt` indexing every reference page as markdown, the MCP server itself, and an Agent Skills API at `/v1/ai/skills/{id}`. Clause 7 is met by personal access tokens and OAuth tokens carrying introspection, refresh and revocation, with `List personal access tokens in a workspace` and `Revoke a personal access token in a workspace` letting an administrator end an agent's credential without touching anyone's session. What no surface reaches is the authorization plane. The main API publishes 48 paths and the Admin API 32, and between them nothing sets a permission level on a page, database, data source or teamspace. The Admin API builds groups at `/v1/spaces/{space_id}/groups` and fills them at `.../members`, which is the identity plane [contributing.md](contributing.md#verifying-clauses-2-and-3) says may be delegated, while `/v1/spaces/{space_id}/agents/{agent_id}/permissions` grants sharing on a Custom Agent and has no equivalent for content. The CLI documents no share or permissions command, and Notion's own MCP tool reference records that no tools for managing permissions, sharing settings or granular access control exist. An agent can therefore create a database, add properties across several types and fill it, and then cannot say who may see it, so sharing is a step only the interface can take, and granting access is one of the three things clause 2 names an operator as having to do. Because both OpenAPI documents index every path Notion serves, the absence is a finding rather than an argument from silence, and it is a gap rather than a refusal, since an organization bot token carrying every admin scope meets the same wall as a personal one. **Would qualify with** an endpoint that grants a person, group or teamspace a permission level on a page or database.
- [OpenStatus](https://www.openstatus.dev) - Fails clause 3. Configuration is not where it falls short: the v2 API at `api.openstatus.dev/openapi.json` creates HTTP, TCP, DNS, ICMP and gRPC monitors, status pages with their components and component groups, status reports, maintenance windows, notification channels and private locations, which is most of what the dashboard does. Reading is. `ListMonitors` takes no parameters at all, and the other list operations are the same shape, so there is no granular filtering and no search over the model, which is the second half of clause 3 rather than a detail of it. Workspace members, their roles and API keys have no endpoints either, so the grant the round trip weighs most heavily is a dashboard act. Clause 6 is comfortably met by the published document, and clause 4 by the web app and the public status pages. **Would qualify with** filters and search on the list operations, and workspace member endpoints.
- [Prosaic](https://www.prosaic.works) - Fails clause 2. General ledger for New Zealand accounting firms, with a firm dashboard and a branded client portal at `app.prosaic.works`, so clause 4 is met by a shipped interface rather than left to the API. The books half is sound. The OpenAPI document at `beta.prosaic.works/api/docs/openapi` creates entities, chart-of-accounts templates and child accounts, contacts, manual journals, invoices, fixed assets and rules, reconciles and reverses bank transactions, and reads the general ledger, trial balance, balance sheet and profit and loss. The model is the fixed one bookkeeping calls for, a chart of accounts, tax codes and dimensions rather than user-defined entities, which is parity rather than a gap. Clause 6 is met several times over, by that document, an llms.txt at `developer.prosaic.works/llms.txt`, OpenID and RFC 8414 authorization-server metadata, RFC 9728 protected-resource metadata for its MCP server, and dynamic client registration. What the document does not reach is the access model. Nothing lists, invites or removes a workspace member, assigns a role, or scopes a person to one entity, and the only path about users is `GET /api/public/v1/me`, so an agent can create a client's books and cannot say which staff may work on them. Clause 7 fails for a related reason: keys are created under Settings, Users, Manage API keys, by owners and admins only, and the document says "A key acts as its user and can reach every workspace that user belongs to", while the OAuth scopes are `openid`, `profile`, `email` and `offline_access`, none of them narrower than the user. **Would qualify with** endpoints for workspace members, roles and per-entity access, and keys or scopes narrower than the user who created them.
- [Recall](https://www.recall.it) - Fails clause 2. Formerly getrecall.ai, and the clearest read-only case on this page, because both machine surfaces say so in their own words. The API is three endpoints, `GET /api/v1/cards`, `GET /api/v1/cards/{card_id}` and `GET /api/v1/search`, under the line "The API currently supports read-only operations. A write API is on the roadmap, stay tuned." The hosted MCP server at `backend.getrecall.ai/mcp/` is four tools, `search`, `filter_by_metadata`, `get_document_content` and `explore_kb`, under "The MCP server currently provides read-only access to your knowledge base. Write capabilities are coming soon", and the single scope it asks for is `kb:read`. Meanwhile the web app is where a person creates cards, edits the text the model generated, retags it and links one card to another, so an operator cannot put anything into the knowledge base at all without the web app, which is the whole of the product. Nothing else here is weak: filtering is granular, semantic search covers the whole knowledge base rather than one endpoint per screen, clause 4 is comfortably met by the web app and the browser extension, and clause 7 is met twice, by OAuth authorization in the browser with no key to copy and by `sk_` keys carrying expiries from 30 days to never, ten active per account. **Would qualify with** the write API and the MCP writes already on its roadmap.
- [SmartSuite](https://www.smartsuite.com) - Fails clause 2. The schema half holds up: the REST API creates solutions and tables, adds fields singly and in bulk, updates and deletes them, and creates views, so an agent can build the model it is about to work against. Roles are the fixed set of Admin, Solution Manager, General, System and Guest, which is no gap in itself, since [contributing.md](contributing.md#verifying-clauses-2-and-3) says that where the roles are a fixed set, assigning an existing one is the whole of the test. What has no machine form is the assigning, nor the grant beneath it. Org Management documents six pages, the member object, list members, update member, the team object, list teams and add team, and nothing beside them: no endpoint reaches solution, table or field permissions, which the help centre puts in the Manage Solution Permissions dialog, and the update-member page does not say that `role` is writable. An agent can therefore create a table and cannot say who may see it. Re-read under the operator wording: granting access is one of the three things an operator must do, and neither half of it has a machine form here, so the verdict is unchanged. Six pages is a thin section to argue from silence over, so this is the entry here most likely to be wrong. A link to a permissions endpoint would settle it, and under the round-trip rule in [contributing.md](contributing.md#verifying-clauses-2-and-3) this is the entry on this page where running it would settle more than further reading. Clause 6 has nothing to point at either, since `developers.smartsuite.com/llms.txt` returns the documentation site's own shell rather than an index, no OpenAPI document is published, and the MCP server in circulation is SmartSuiteFoundry's rather than SmartSuite's, which makes it a connector under the scope rules. Clause 7 fails as well, because an API key is a user's key carrying "the same permissions as the user generating the key", so the documented pattern is spending a seat on an API member account rather than issuing an agent a credential of its own, leaving clause 5 to carry the one-of requirement. **Would qualify with** endpoints for solution or table permissions and documented role assignment.
- [Tailor](https://www.tailor.tech) - Fails clause 4. Headless ERP that markets itself as "designed for humans and AI agents alike", and the machine half holds up: TailorDB types, fields and per-operation permissions are declared in the first-party TypeScript SDK and applied with `tailorctl`, which is a shipped command an agent runs itself, and the GraphQL API is generated from that schema. What it does not ship is an interface for the people whose records these are. The Console manages the workspace and inspects deployed resources, the GraphQL Playground is a developer tool, and the operational frontend is something you build. AppShell, the current framework, calls itself an "opinionated React application framework for creating applications on Tailor Platform", and its documentation has developers declare modules and resources in TypeScript and supply their own page components. The platform page lists "Generate UI from Schema" as coming soon, and offers out-of-the-box applications to customize "whether you build them yourself or we build it for you". That is clause 4's "reaching your own data should not require building a client first", judged against finance and operations staff rather than developers. **Would qualify with** a shipped operational interface for working with the records.
- [Trigger.dev](https://trigger.dev) - Fails clause 1 under the scope rules in [contributing.md](contributing.md#not-on-this-list). **The earlier reason has been withdrawn.** This was recorded as failing clause 2 because reaching a new task means `trigger.dev deploy` building and redeploying a worker. Clause 2 now asks whether an operator can run the software with only an agent, assessed against an agent that runs repository workflows, and no admin interface defines a task either: the dashboard shows runs, traces, schedules and environment variables and authors nothing, so there is no operation here that only a person can reach. The machine half is broad, with 51 paths in the published OpenAPI document covering runs and their traces, schedules, environment variables, queues and concurrency, deployments, batches, bulk actions and waitpoint tokens, plus `/api/v1/query` and `/api/v1/query/schema`, which describe what is queryable at runtime. What rules it out is scope. It describes itself as a way to "build and run durable AI agents and workflows in TypeScript", which is the orchestrator side covered by the readme's Related Lists. **Would be reconsidered if** the case is made that a durable execution platform is the producer side rather than the consumer side, which is a judgement about the scope rules rather than about the clauses.
- [Typebot](https://typebot.io) - Fails clause 2. The builder API is better than most visual products manage: 35 documented operations create, import, update, publish and unpublish typebots, so the flow a person draws is a document an agent can write, and folders, workspaces and results are all reachable. Membership is where it stops. `List members` is the only member operation in the reference, while the documentation has a person add members and guests in the workspace screen, so an agent can build a bot and cannot give anyone access to it. Clause 6 is met by the builder OpenAPI document at `/openapi/builder.json`. **Would qualify with** endpoints that invite a member and set their role.
- [Unkey](https://unkey.com) - Fails clause 2. The authorization plane is exactly what this list asks for: `permissions.createPermission`, `permissions.createRole` and `permissions.setRolePermissions` define the vocabulary, `keys.addRoles` and `keys.setPermissions` attach it to a credential, and identities, API namespaces, ratelimit overrides, projects, deployments, domains, environment variables and gateway policies sit in the same v2 surface, so the deploy product is as machine-callable as the key product. What that specification leaves out is access to Unkey itself. Root keys are the credentials that reach all of it, and each carries per-resource permissions such as `api.<id>.verify_key`, so issuing one is how an operator grants an agent access narrower than full. The root key documentation describes creating, rotating and deleting them only as steps under Settings, and the generated OpenAPI document has no root key path. Issuing the first root key is the bootstrap step [contributing.md](contributing.md#verifying-clauses-2-and-3) excuses, but issuing the next, scoped to one API for another agent, recurs, and it is the per-resource grant the round trip weighs most. The audit log is also readable only in the dashboard, which on its own would not fail it, since reading history is not something an operator needs to run the software. Clause 6 is met by the published OpenAPI document and clause 7 by workspace root keys carrying their own permissions. **Would qualify with** root key creation, rotation and deletion in the API.
- [Beads](https://github.com/gastownhall/beads) - Fails clause 4. Ticketing is squarely in scope and it passes clause 2, because issue types come from `.beads/config.yaml` and an operator runs the whole product from the CLI. But it ships no human interface: `bd human` is a subset of the same CLI that serves as its machine interface, `bd serve` is "the beads HTTP API over loopback", and every graphical UI is community-built. Counting one CLI as both interfaces would make clause 4 self-satisfying. **Would qualify with** a shipped human surface.
- [OpenChatCut](https://github.com/0xsline/OpenChatCut) - Meets clauses 1 to 4 but fails the requirement to meet at least one of clauses 5, 6 and 7. It is explicitly single-user and local, so there is no authorization model to enforce, its agent credential is a static bearer token rather than a scoped identity, and its skills index sits in `~/.openchatcut/skills/` rather than being published. **Would qualify with** a multi-user permission model or per-agent credentials.

## Eligible, pending evidence

These meet the clauses on everything the published material settles, and turn on one question it leaves open. They are neither listed nor ruled out until someone answers it, with a link to the documentation page, the generated schema or the runtime metadata that does, or with a round trip where nothing published will.

- [Strapi](https://strapi.io) - **The earlier reason has been withdrawn.** This was recorded as failing clause 2 because the Content-Type Builder "is only accessible to create and update content-types when your Strapi application is in a development environment, else it will be in a read-only mode in other environments", so a running production instance cannot define content types. That is symmetric: in production the builder is read-only for a person too, and no operation there is reserved to clicking. Content types are schema files in the repository, and an agent with a shell writes them and deploys, which counts under the reference agent in [contributing.md](contributing.md#gate-one-the-definition). The open question is the half that was never assessed. Granting access is one of the three things an operator must do, and nothing checked so far shows whether the Users and Permissions roles and their per-content-type permissions are reachable without the admin panel. **Would be settled by** a documented endpoint or command that creates a role and sets its permissions on a content type, or a round trip that defines a content type, deploys it to a running instance, grants a narrowed role and operates against it.

## Now listed

Assessed here first, and since moved into the readme. The reasoning is kept so the change is visible rather than silent.

- [ERPNext](https://erpnext.com) and the [Frappe Framework](https://frappeframework.com) underneath it - **Now listed, under Enterprise Resource Planning.** Recorded here earlier as eligible pending evidence, on the open question of whether an agent can create a DocType, and therefore the model itself, through the API, since neither the REST API reference nor the Manipulating Documents guide documents schema creation. Frappe's own source settles it. `DocType` is a DocType, so `POST /api/resource/DocType` reaches the same controller the Desk interface saves through, and that controller's `check_developer_mode` refuses only standard DocTypes outside developer mode, with the message "Not in Developer Mode! Set in site_config.json or make 'Custom' DocType", so a DocType created with `custom: 1` is allowed on a production instance for an agent exactly as for a person. `Custom Field` extends the DocTypes ERPNext ships. The access half runs through the same API, because `Role`, `Custom DocPerm` and `User Permission` are DocTypes too, which covers defining a role, granting it on one DocType and restricting a user to particular records. Clause 3 is met at runtime by `GET /api/v2/doctype/<doctype>/meta` in the version-15 and version-16 branches, returning each field's label, type and description, with granular `filters` and `or_filters` on every list and full-text search through `frappe.utils.global_search.search`. Clause 6 is met by the OAuth2 update merged as frappe#33188, which added RFC 8414 authorization-server metadata, RFC 7591 dynamic client registration and RFC 9728 protected-resource metadata, and clause 7 by an agent being its own User with its own roles and an API key it can issue through the whitelisted `generate_keys`, so assignments and version history name it. The earlier notes still hold: `frappe/mcp` is first party but a library for building MCP servers inside Frappe apps, documented as highly experimental and not shipped by ERPNext, and OpenAPI generation remains a third-party app. Settled by reading the source rather than by a round trip, since the controller and the meta endpoint answer the question the documentation left open.
- [monday.com](https://monday.com) - **Now listed, under Project and Work Management.** Recorded here earlier as failing clause 2 because custom account roles, on the Enterprise plans that offer them, are created only in the admin interface, and the `account_roles` reference carries a query with no mutation beside it. That is still true, and it is the narrow gap [contributing.md](contributing.md#verifying-clauses-2-and-3) describes rather than a failure: the per-resource grant is weighed above the role definition, and every per-resource grant is reachable. `create_team` and `add_teams_to_board` build the grouping and attach it to a board, `update_teams_board_role` and `update_users_board_role` set a team's or a person's role on it, `set_board_permission` sets the board default, and `update_users_role` assigns any account role, custom ones included. Below Enterprise the account roles are a fixed set, and assigning one is the whole of the test. The model half was never in doubt: `create_board`, `create_column`, `change_column_metadata` and `delete_column`, views through the Platform MCP, and `get_column_type_schema` describing each column type at runtime.
- [Palantir Foundry Ontology](https://www.palantir.com/docs/foundry/ontology/overview) - **Now listed, under Data Platforms.** Recorded here earlier as failing clause 2, on the grounds that ontology-as-code through SuperRepos is "a repository workflow a person deploys, not an interface an agent calls". That reason has been withdrawn on both halves. A repository workflow is something the reference agent in [contributing.md](contributing.md#gate-one-the-definition) runs itself, and the mechanism was described wrongly: SuperRepo declares object types, links, interfaces and actions in TypeScript, is creatable "in the Palantir platform or from the Foundry CLI", and deploys through the Foundry CLI and any CI provider, with types created in code appearing in the UI and UI-created types importable into code. Checked against Palantir's SuperRepo and platform API documentation. Note that Palantir documents SuperRepo as being in beta and as possibly unavailable on a given enrollment; the entry is listed on the basis that the path is reaching general availability, and maturity is not a criterion on this list in any case.
