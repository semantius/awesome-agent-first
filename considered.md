# Considered, not listed

Every candidate assessed for this list that did not end up in the readme, why, and what would change that. Checked 2026-09-22, with the entries below dated 2026-09-23 added on that date.

This file exists because an inclusion rule nobody can see being applied is just a claim. Nothing here is a criticism of the software. Several of these are better built and more widely used than entries that did qualify, and a few fail on something as small as a missing licence file. "Not listed yet" is meant literally: say so in an issue when one of these changes and it gets re-checked.

The criteria are in [contributing.md](contributing.md). Software that fails clause 4 by design is recorded separately in [agent-only.md](agent-only.md), because being built agent-only is a decision rather than a shortfall.

**Corrections are welcome and will be made quickly.** Every claim here was checked against the project's own repository, documentation or a live response on the date given, and is a snapshot of what was public then. That method is fallible in three ways: a capability can exist somewhere the check did not look, undocumented behaviour is invisible to it, and everything here goes stale as projects ship. If something is wrong about your project, open an issue or a pull request with a link to what shows otherwise. Factual corrections are not argued with. Judgement calls, meaning whether a clause is the right clause, are worth discussing in the open, and that discussion belongs in an issue where everyone can read it.

## Fails a clause

- [agent-desk](https://github.com/huabeitech/agent-desk) - Fails clauses 2 and 3. The MCP server it ships at `/api/mcp` registers two tools, `server_time` and `service_info`, and `internal/ai/mcps/registry.go` leaves a comment where further providers would go; the working MCP integration is the client that lets its own AI agent call external tools, which is the consumer direction rather than a way in. The dashboard's HTTP surface does reach roles, permissions, tickets and knowledge bases, but nothing documents it: the documentation site has no API reference, `llms.txt` and `.well-known/mcp.json` both return 404, and the "Open API" in the channel settings is OpenIM, a chat channel. Authorization is enforced server-side, which satisfies clause 5, but authentication is a password login issuing a session token, with no credential an agent could hold. **Would qualify with** an OpenAPI document over the dashboard routes and MCP tool providers covering tickets, conversations and knowledge.
- [Relaticle](https://github.com/relaticle/relaticle) - Fails clause 2. Custom field definitions are read-only everywhere they are reachable: the MCP server offers `list-custom-fields-tool` and `get-crm-schema-tool` with no write equivalent, `CustomFieldsController` implements only `index`, and no console command defines one. Creating a custom field requires the Filament admin panel, which is clause 2's "an API covering a subset of what the interface can do". **Would qualify with** a writable custom-fields endpoint or MCP tool.
- [Palantir Foundry Ontology](https://www.palantir.com/docs/foundry/ontology/overview) - Fails clause 2. Object, link and action types are created in Ontology Manager, and the platform API reads the ontology without being able to define it. Ontology-as-code through SuperRepos is a repository workflow a person deploys, not an interface an agent calls. **Would qualify with** the ontology modification endpoints Palantir has said are in progress.
- [Agentic Postgres](https://www.tigerdata.com/blog/postgres-for-agents) - Fails clause 4 under the audience test. Its human paths are psql, third-party SQL clients and the console SQL editor, which are database administration tools rather than interfaces for the people whose records live there. **Would qualify with** a shipped interface for working with the data as records.
- [Strapi](https://strapi.io) - Fails clause 2. Checked 2026-09-23. The Content-Type Builder is gated on the `strapi develop` command rather than on `NODE_ENV`, and its own documentation states it "is only accessible to create and update content-types when your Strapi application is in a development environment, else it will be in a read-only mode in other environments". A running production instance therefore cannot define the content types, components or fields that the same product defines in development, which is clause 2's "an API covering a subset of what the interface can do". **Would qualify with** content-type and component definition reaching a running instance.
- [Tailor](https://www.tailor.tech) - Fails clause 4. Checked 2026-09-23. Headless ERP that markets itself as "designed for humans and AI agents alike", and the machine half holds up: TailorDB types, fields and per-operation permissions are declared in the first-party TypeScript SDK and applied with `tailorctl`, which is a shipped command an agent runs itself, and the GraphQL API is generated from that schema. What it does not ship is an interface for the people whose records these are. The Console manages the workspace and inspects deployed resources, the GraphQL Playground is a developer tool, and the operational frontend is something you build, with Fabrix generating components from the GraphQL schema and AppShell as a starting point. That is clause 4's "reaching your own data should not require building a client first", judged against finance and operations staff rather than developers. **Would qualify with** a shipped operational interface for working with the records.
- [Beads](https://github.com/gastownhall/beads) - Fails clause 4. Ticketing is squarely in scope and it passes clause 2 vacuously, because issue types come from `.beads/config.yaml` and there is no admin UI for an API to fall short of. But it ships no human interface: `bd human` is a subset of the same CLI that serves as its machine interface, `bd serve` is "the beads HTTP API over loopback", and every graphical UI is community-built. Counting one CLI as both interfaces would make clause 4 self-satisfying. **Would qualify with** a shipped human surface.
- [OpenChatCut](https://github.com/0xsline/OpenChatCut) - Meets clauses 1 to 4 but fails the requirement to meet at least one of clauses 5, 6 and 7. It is explicitly single-user and local, so there is no authorization model to enforce, its agent credential is a static bearer token rather than a scoped identity, and its skills index sits in `~/.openchatcut/skills/` rather than being published. **Would qualify with** a multi-user permission model or per-agent credentials.

## Eligible, pending a round trip

These meet the clauses on everything the documentation settles, and turn on behaviour only a live instance can confirm. They are neither listed nor ruled out until someone runs the round trip in [contributing.md](contributing.md#verifying-clauses-2-and-3) and reports it.

- [ERPNext](https://erpnext.com) and the [Frappe Framework](https://frappeframework.com) underneath it - Checked 2026-09-23. Frappe generates a REST API for every DocType and the Desk interface is a client of that same API, which is a strong clause 2 story, and role permissions and user permissions are enforced server-side for clause 5. The open question is whether an agent can create a DocType, and therefore the model itself, through the API. `DocType` is a DocType, so `POST /api/resource/DocType` ought to work, but neither the REST API reference nor the Manipulating Documents guide documents schema creation or any metadata endpoint, and both cover document instances only. Note also that every Frappe MCP server found was third party, so they are connectors under the scope rules, and OpenAPI generation is likewise a third-party app rather than something Frappe publishes about itself. **Would be settled by** a round trip creating a DocType, adding fields, creating a Role and a narrowed Custom DocPerm, and operating against them, run against a fresh instance.

## Fails the quality bar

Each of these meets enough of the definition to be worth re-checking. All four fail on licence or maintenance, which are the easiest things on this page to fix.

- [cluster-software/agent-crm](https://github.com/cluster-software/agent-crm) - No licence detected, last push 2026-06-05. The most adopted of the unlicensed candidates at 118 stars. **Would qualify with** a licence file.
- [keshav55/agent-crm](https://github.com/keshav55/agent-crm) - No licence detected, last push 2026-08-28, so actively worked on. **Would qualify with** a licence file.
- [agentsfirst](https://github.com/capitalthought/agentsfirst) - No licence detected on the repository, last push 2026-06-16. The framework it documents is still cited under Assessment and Reading, because reference material is not held to the software gates.
- [pg-mcp-server](https://github.com/stuzero/pg-mcp-server) - Last push 2025-09-10, beyond the six-month line, and a connector over PostgreSQL rather than a product.

## Out of scope

- [BigQuery](https://cloud.google.com/bigquery) - Meets the clauses and is excluded on curation. What makes it eligible, DDL, `GRANT` and `REVOKE`, row access policies and `INFORMATION_SCHEMA`, is equally true of Snowflake, Databricks, Redshift, ClickHouse and PostgreSQL itself, so admitting it admits every cloud database. Its agent-specific capability, BigQuery Graph, was in preview when this was checked. **Would qualify with** generally available capability built for agents rather than generic administrability.
- [Bonnard](https://bonnard.ai) - The agentic semantic layer assessed here was archived on 2026-07-03, and its repository now points to a different current product. That product, `@bonnard/mcp-charts`, is an SDK that "adds interactive charts to any MCP server". It fails clause 1: a library a developer embeds in their own server, which neither holds nor governs data of its own.
- [DuploCloud AI Help Desk](https://duplocloud.com/blog/ai-help-desk-for-devops/) - Fails clause 1. The product is the agents: AI DevOps Engineers specialized in Kubernetes, observability, compliance and cost, with the help desk as the queue people file requests into. The platform underneath, Automation Studio with `duploctl` and a first-party MCP server, is a separate candidate, and it provisions cloud infrastructure rather than holding an organization's records. The centralized MCP server fronting Kubernetes, cloud providers, OpenTelemetry and CI/CD is a connector over someone else's system.
- **Cloudflare Workers and Vercel AI Gateway** - Runtime infrastructure an agent calls in passing rather than software holding an organization's records. Covered by the lists under Related Lists in the readme.
