# Considered, not listed

Every candidate assessed for this list that did not end up in the readme, why, and what would change that.

This file exists because an inclusion rule nobody can see being applied is just a claim. Nothing here is a criticism of the software. Several of these are better built and more widely used than entries that did qualify, and a few fail on something as small as a missing licence file. "Not listed yet" is meant literally: say so in an issue when one of these changes and it gets re-checked.

The criteria are in [contributing.md](contributing.md). Software that fails clause 4 by design is recorded separately in [agent-only.md](agent-only.md), because being built agent-only is a decision rather than a shortfall.

**Corrections are welcome and will be made quickly.** Every claim here was checked against the project's own repository, documentation or a live response, and is a snapshot of what was public when it was checked. That method is fallible in three ways: a capability can exist somewhere the check did not look, undocumented behaviour is invisible to it, and everything here goes stale as projects ship. If something is wrong about your project, open an issue or a pull request with a link to what shows otherwise. Factual corrections are not argued with. Judgement calls, meaning whether a clause is the right clause, are worth discussing in the open, and that discussion belongs in an issue where everyone can read it.

## Fails a clause

**Re-assessment pending.** Clause 2 now asks whether an agent can do everything a user does without falling back to a browser, and treats administration as good practice. ERPClaw failed it on administration and is to be re-assessed under that wording; its verdict stands until then.

- [agent-desk](https://github.com/huabeitech/agent-desk) - Fails clauses 2 and 3. Self-hosted support desk whose staff work, taking over conversations, replying, transferring, linking customers, raising and moving tickets and maintaining the knowledge base, runs through the dashboard's HTTP routes in `internal/bootstrap/routes.go`. Those routes accept the bearer token a password, OIDC or WeCom login issues, but nothing documents them for a caller: the documentation site has no API reference, `llms.txt` and `.well-known/mcp.json` return 404, and the "Open API" channel is an inbound channel for customers' messages. The MCP server at `/api/mcp` registers two tools, `server_time` and `service_info`, with a comment in `internal/ai/mcps/registry.go` where further providers would go; the rest of its MCP support is the client its own AI agent uses to call external tools. Authorization is enforced server-side through roles and permissions, which meets clause 5. **Would qualify with** an API reference or OpenAPI document over the dashboard routes, or MCP tools covering conversations, tickets and the knowledge base, with guidance an agent can follow.
- [Relaticle](https://relaticle.com) - Fails clause 2. Companies, people, opportunities, tasks and notes are fully reachable through the REST API at `api.relaticle.com/v1`, described by `relaticle.com/openapi.json`, and the MCP server at `mcp.relaticle.com`, with OAuth discovery served for both. Email is not. Members read and reply to synced email on a record, send one email to many people, and link synced meetings to records, and the vendor's MCP reference says "the server exposes CRM records only: it does not send email or read synced mail and meetings", which its llms.txt repeats. Custom fields are still defined only in the interface, which is administration and so good practice rather than a condition. **Would qualify with** endpoints or MCP tools that read, reply to and send email, and read and link meetings.
- [Airtable](https://airtable.com) - Fails clause 2. Records, comments, attachments, forms and interface pages are all reachable: the Web API indexed at `airtable.com/developers/web/llms.txt` creates, updates and deletes records and comments and uploads attachments, and the first-party MCP server at `mcp.airtable.com/mcp` adds keyword search, form submission, interface pages and draft automations. What it leaves to the interface is the view. Airtable's help centre says Editors "can create, delete, modify, and print views", and collaborative views are shared configuration that automations trigger on and webhooks watch, but the Web API offers only List views, Get view metadata and Delete view, and the MCP server only `list_views_for_table`. Because that llms.txt indexes every endpoint and the MCP tools reference lists every tool, the absence is a finding rather than an argument from silence. Retyping a field, editing select choices and deleting a field have no machine form either, and automations created over MCP stay "off until the user reviews and turns it on in the Airtable UI", but that is administration and so good practice rather than a condition. Clause 6 is met by that llms.txt tree and by RFC 9728 and RFC 8414 metadata, and clause 5 by an MCP server that "enforces the same permission boundaries as the Airtable UI and REST API". **Would qualify with** view creation and configuration (filters, sorts, grouping and visible fields) through the Web API or the MCP server.
- [AnythingLLM](https://anythingllm.com) - Fails clause 1. The product is the assistant: the vendor now describes it as "a free, private AI assistant that runs on your device" and its repository as "a powerful local-first agent experience", with agent skills, agent flows and an MCP integration that is a client reading `anythingllm_mcp_servers.json` to call other servers, which is the consumer direction rather than a way in. The machine half is not where it falls short: `server/swagger/openapi.json` publishes the AnythingLLM Developer API over workspaces, threads, documents, embeds and users, with `POST /v1/workspace/{slug}/vector-search` for retrieval and `POST /v1/admin/workspaces/{workspaceSlug}/manage-users` for a per-workspace grant, though keys are instance-wide and "anyone with the API key can use the AnythingLLM API". The workspace store underneath is the memory-store category the readme's Related Lists already serve. **Would qualify with** a first-party MCP server or API over its own workspaces, offered as the product and governed by per-user permissions.
- [Attio](https://attio.com) - Fails clause 2. Records, lists and entries, notes, tasks, comments, files, meetings and call recordings are reachable through the REST API described at `api.attio.com/openapi/api` and the first-party MCP server at `mcp.attio.com/mcp`, which adds full-text and semantic search and grouped reports. Sending is what neither reaches. The help centre's Send emails in Attio is "available for all workspace members", from a person's record or as a mass send, and sequences enrol recipients from an "Enroll to sequence" button, but the OpenAPI document's only email path is `GET /v2/emails`, whose content "is never returned", its only sequences path adds addresses to the unsubscribe list, and the MCP server's email tools search and read. Update a task changes "only the `deadline_at`, `is_completed`, `linked_records`, and `assignees` fields", saved views are listable without being creatable, and workflows and dashboards have no endpoints. Because the OpenAPI document covers every path and the MCP overview lists every tool, these absences are findings. Object permissions remain interface-only, which is administration and so good practice. Clauses 4, 5, 6 and 7 are met. **Would qualify with** endpoints or MCP tools that send an email from a record and enrol records in a sequence.
- [Budibase](https://budibase.com) - Fails clause 2. The record half is sound: the public API in `packages/server/specs/openapi.yaml` creates, updates, deletes and retrieves rows, searches them with `string`, `fuzzy`, `range` and `equal` filters combined by `allOr`, searches through a view and executes a saved query. What it does not run is the workflow a user drives from an app. Row actions, which the documentation says "are used for creating and progressing workflows", are triggered by clicking them in a table or view, and the On demand trigger "runs when invoked from the UI of your Budibase application, or by an agent workflow"; the reference has no operation that triggers either, and none for automations at all, so only an automation built with a webhook trigger can be started from outside. The server routes `POST /api/tables/:sourceId/actions/:actionId/trigger` internally, but nothing Budibase publishes documents it. Roles and per-resource grants remain interface-only beyond the enterprise `POST /roles/assign`, a good-practice gap rather than the failure. API keys are generated per user in the portal, and no first-party MCP server was found. **Would qualify with** published operations that trigger a row action and an on-demand automation.
- [Documenso](https://documenso.com) - Fails clause 2. The sending half is fully machine-callable: the v2 OpenAPI document at `app.documenso.com/api/v2/openapi.json` covers envelopes, documents, templates, fields, recipients, attachments, folders and direct links, `GET /envelope` takes a `query` search beside status, type, template and folder filters, envelopes can be distributed, redistributed, cancelled and duplicated, and audit logs and certificates download per envelope. The receiving half is not. Users are sent documents "to sign, approve, or view", and the developer guide states that "The API cannot: Sign documents on behalf of recipients (recipients must sign themselves)"; the only recipient action in the reference records a rejection made "outside of the platform", so an agent holding a user's access falls back to the signing page for that user's own step. The documented reason is that "Signers must actively interact with signature fields to apply their signature", which makes the remedy a scope rather than an endpoint. Teams, members, webhooks and tokens are web-app only too ("The V2 REST API does not expose `/team/*` endpoints"), a good-practice gap rather than the failure. Clause 6 is met by that document, and team-scoped tokens carry clause 5. **Would qualify with** a way for the authenticated recipient to complete their own signing, approval or view step through the API, behind a scope of its own.
- [Dosu](https://dosu.dev) - Fails clause 2. Engineering knowledge base with strong discovery (an llms.txt addressed to agents, a public OpenAPI document at `api.dosu.dev/openapi.json`, `auth.md`, RFC 9728 metadata and a hosted MCP server) and a CLI whose bundled agent skill reaches most of what a member does: `dosu docs` creates, updates, archives, restores, imports and publishes Documents, `dosu review` approves, edits, rejects and reverts drafts, `dosu ask` and the MCP `read_knowledge` tool search, and administration such as creating Libraries and Agents and inviting members is reachable too. What stays in the interface is organizing that knowledge. The Topics guide has a person create Topics and "add or remove Topics on any Document yourself", while the vendor's own CLI reference states "Topics are read-only" and that there is "no suggestion-accept command", the page update schema carries only title, body, published and description, and no MCP tool touches Topics. Clause 1 is borderline rather than failed, since much of the product is Dosu's own agent answering on GitHub and Slack, but since September 2026 it has retired its hosted labeling and stale bots and describes itself as a knowledge base. **Would qualify with** creating, editing and assigning Topics through the CLI, API or MCP server.
- [ERPClaw](https://www.erpclaw.ai) - Fails clause 2, and clauses 5 and 7 with it. Open-source ERP covering the general ledger, order to cash, source to pay, inventory, payroll and tax, whose every operation is an action behind one entry point, `scripts/db_query.py --action {action} --args`, run as local Python against the database. It is not single-device software: the README says "SQLite by default, PostgreSQL fully supported … point it at PostgreSQL when you outgrow a single file", so a shared deployment is possible. The access model is what stops it. Users and roles exist, with `add-user`, `update-user`, `add-role`, `assign-role` and `seed-permissions` among the actions and a `company_ids` list restricting a user to particular companies, but nothing sets what a role permits beyond the seeded defaults, so a role an agent defines grants nothing it can shape. Nor does the engine enforce the grants it holds. `erpclaw_lib/rbac.py` says "RBAC is opt-in. Skills call require_permission() in actions that need enforcement", and allows every action while no user exists, and the dispatcher's only permission action is `check-telegram-permission`, which a front end asks before acting. The caller is not authenticated either, since an action receives no credential and a user id is whatever the caller passes, so any process with a shell reaches everything and an agent cannot hold a credential of its own. The README is candid about this, saying identity and authorization "are being built out alongside Atrium", its own agent loop. ERPClaw Web adds JWT sign-in and role-based access, but as a FastAPI proxy in front of the same scripts, so it governs only the callers that go through it. Clause 1 is mixed as well, because the product ships as a skill for the OpenClaw and Hermes agent runtimes and its primary interface is the assistant. **Would qualify with** authorization enforced in the dispatcher for every action, callers authenticated with credentials of their own, and an action that sets what a role permits.
- [Formbricks](https://formbricks.com) - Fails clause 2. Survey and response work is well covered: the v1 and v2 management APIs and the v3 API, which its reference calls "private beta" and "unlisted", create, patch, archive and delete surveys, list, update and bulk-delete responses, run workflows and manage tags, and a first-party MCP server at `app.formbricks.com/api/mcp` serves survey, workflow and feedback-record tools behind OAuth 2.1 with a scope per group. Contact attribute keys and teams now have write endpoints. What stays in the interface is analysis and targeting work: Dashboards & Charts, documented as how feedback is visualised and shared, have no operation in any of the three references, segments can be named in a survey's targeting but not created, edited or deleted, and contacts cannot be deleted. Of response filtering, the v3 reference says per-answer, hidden-field, metadata, contact-attribute, quota and tag filters "are not offered" and that "the in-app dashboard does offer them, so this API is knowingly behind the dashboard here". Clauses 3, 5 and 6 are met, and organization API keys scoped per workspace carry the credential half of clause 7. **Would qualify with** published operations for dashboards, charts and segments, contact deletion, and the response filters the dashboard offers.
- [Notion](https://www.notion.com) - Fails clause 2. Records, views, files, meeting notes and Custom Agent sessions are all reachable: the REST API creates databases, edits data source properties and manages views, the hosted MCP server adds content search through `notion-search` and `notion-ai-search`, duplication and selection-anchored comments, and the `ntn` CLI and personal access tokens give an agent a user's own credential, so clauses 5, 6 and 7 are met several times over. What only the interface reaches is ordinary user work. Notion's help centre says anyone with full access can "share the page with anyone they want" from the Share menu, and neither the public OpenAPI, the Admin API, the MCP tool reference nor the CLI shares a page or database with a person, group or teamspace; the only route that does, `PATCH /v1/_/pages/{page_id}/permissions`, sits in `openapi-undocumented.json` under "Internal/undocumented Notion API endpoints. These endpoints are not part of the public API". Resolving and re-opening a comment thread, which the help centre describes as a click on any comment, has no endpoint or tool either, and the comments guide lists re-opening resolved comments as something only the interface does. Administration is not the finding: groups, members and personal access tokens are in the Admin API. **Would qualify with** a public endpoint or MCP tool that shares a page or database at a permission level, and one that resolves and re-opens comment threads.
- [Prosaic](https://www.prosaic.works) - Fails clause 2. General ledger for New Zealand accounting firms, with a firm dashboard and client portal at `app.prosaic.works`, so clause 4 is met by a shipped interface. Much of the books is reachable: the OpenAPI document at `app.prosaic.works/api/docs/openapi`, which the MCP server at `mcp.prosaic.works/mcp` wraps, creates entities, contacts, chart-of-accounts accounts and templates, manual journals, finalised invoices, fixed assets, rules and scheduled tasks, reconciles and reverses bank transactions, and reads the ledger and reports. What it leaves to the app is user work. GST returns are read-only, and the help centre says "finalising and filing with IRD happen in the app", as do amending, exporting and emailing a return. Comments on transactions, returns and journals, which is how a firm chases a client for a receipt, have no endpoint, and neither do report packs, the year-end statements a firm publishes. Invoices can be created finalised and read, but not drafted, edited, sent or voided, and fixed assets cannot be updated or disposed of. Clause 5 is met by workspace roles and per-entity access, which the MCP server inherits, and clause 6 by that document, `llms.txt`, OpenID, RFC 8414 and RFC 9728 metadata and dynamic client registration. Clause 7 is not, since a key "acts as its user" and the OAuth scopes are `openid`, `profile`, `email` and `offline_access`. **Would qualify with** endpoints to finalise, file, amend and share GST returns, to comment on transactions and returns, and to build and publish report packs, along with invoice and fixed-asset updates.
- [Recall](https://www.recall.it) - Fails clause 2. Personal AI knowledge base whose two machine surfaces say they are read-only in their own words: the API at `backend.getrecall.ai/api/v1` is three GET endpoints under "The API currently supports read-only operations. A write API is on the roadmap", and the hosted MCP server is four `kb:read` tools under "The MCP server currently provides read-only access to your knowledge base. Write capabilities are coming soon." Saving content, writing notes, tagging, linking cards, chatting and quizzing happen only in the apps. The protected-resource and authorization-server metadata now advertise a `kb:write` scope alongside `kb:read`, which the documentation does not yet describe. Clause 4 is met by the web app, extensions and mobile apps, clause 6 by the OAuth metadata and llms.txt, and clause 7 by expiring `sk_` keys. It is a single person's knowledge base with no shared workspace. **Would qualify with** the write API and MCP writes on its roadmap.
- [SmartSuite](https://www.smartsuite.com) - Fails clause 2. SmartSuite now runs a first-party MCP server at `app.smartsuite.com/v1/mcp`, documented in its help centre, that searches and edits records, reads and writes comments, uploads files, updates My Work, edits views and forms, submits forms, and reads and retries automation runs. It sits behind RFC 9728 metadata pointing at an RFC 8414 authorization server, and llms.txt files are served on the marketing site and the help centre, so clause 6 is now met. What neither it nor the REST API reaches is the Communication Center, where "all Roles" send email from a record, or the Button field, whose "When a Button is Clicked" trigger runs an automation for any user with edit rights. The REST reference has no email or button paths and the MCP article names neither, though that article is a summary rather than a tool index and says "the set of capabilities grows regularly", so a `tools/list` on the hosted server is what would settle it. Solution and table permissions remain interface-only, which is administration and so good practice. **Would qualify with** MCP tools or endpoints that send an email from a record and press a button field.
- [Tailor](https://www.tailor.tech) - Fails clause 4. Headless ERP that markets itself as "designed for humans and AI agents alike", and the machine half holds up: TailorDB tables, fields and permissions are declared in the first-party TypeScript SDK and deployed with its `tailor` CLI, the GraphQL API generated from that schema filters and sorts on every field, the same CLI runs queries and workflows, and each application exposes a remote MCP server, in preview, that runs GraphQL as the signed-in user under the same permissions. What it does not ship is an interface for the people whose records these are. The Console offers a GraphQL Playground, schema browsing and the ability to "import and view table data", the operational frontend is something you build with AppShell, an "opinionated React application framework for creating applications on Tailor Platform", and the platform page still lists "Generate UI from Schema" as coming soon, with out-of-the-box applications offered "whether you build them yourself or we build it for you". That is clause 4's "reaching your own data should not require building a client first", judged against finance and operations staff rather than developers. **Would qualify with** a shipped operational interface for working with the records.
- [Tiger Cloud](https://www.tigerdata.com/cloud) - Fails clause 2. Managed Postgres launched for agents as Agentic Postgres, which clears the exclusion for general-purpose databases on two counts: zero-copy forks an agent can take at `POST /projects/{project_id}/services/{service_id}/forkService` or through the `service_fork` tool, and Tiger MCP, which ships inside the Apache-2.0 Tiger CLI under the same login and permissions. Services are created, forked, resized, started, stopped, renamed and deleted, and read replicas, HA, pooling and VPC attachment managed, over the REST API, which the docs call "the complete surface", and data is reached over SQL, through `db_query` and `db_schema`, or any Postgres client. What that surface does not reach is the rest of a Developer's week in Tiger Console. Source connectors that sync from S3, Postgres or Kafka are created, paused, edited and monitored only from the Connectors tab, and the REST reference has no connector resource. Data view, the Console's PopSQL workspace where queries are saved in folders, shared, charted, built into dashboards and scheduled, has no machine form either: PopSQL's own API offers catalog reads and running a query, with a token obtained by contacting them. Clause 3 is well served by `llms.txt`, an agent best-practices page, a cookbook, and MCP tools for documentation search and skills. Clause 4 is met by the Console and by any SQL client, since its users are engineers. Project roles and Postgres roles are enforced server-side, which satisfies clause 5. **Would qualify with** API or MCP coverage of source connectors and of saved queries, dashboards and schedules in Data view.
- [Trigger.dev](https://trigger.dev) - Fails clause 1 under the scope rules in [contributing.md](contributing.md#not-on-this-list). It describes itself as "the open source platform for durable AI agents", ships `chat.agent` for building agents, and is already listed as durable execution infrastructure in awesome-agent-native-services in the readme's Related Lists, which is the runtime and orchestrator side of the line. Clause 2 is not fully met either: the OpenAPI document at `trigger.dev/docs/v3-openapi.yaml`, the CLI and the MCP server cover runs and their traces, bulk actions, error groups, schedules, environment variables, queues and concurrency, deployments, batches, waitpoints, sessions and queries, but alerts, including error-group alerts, and custom dashboards are created only in the dashboard. **Would qualify with** a case that a durable execution platform is the producer rather than the consumer side and that the related lists do not already serve it, together with alert and dashboard management in the API, CLI or MCP server.
- [Unkey](https://unkey.com) - Fails clause 2. API key management, rate limiting and app deployment platform. The v2 OpenAPI document at `api.unkey.com/openapi.yaml`, the `unkey` CLI and the hosted MCP server at `mcp.unkey.com/mcp/v2` cover keys, keyspace creation, identities, roles and permissions, rate limits and overrides, analytics, customer portals and root keys, and on the Compute side projects, apps, environments and their variables, deployments, domains, gateway policies, build logs and request and runtime log queries, and the documentation opens with instructions addressed to agents, so clause 3 is met. What stays in the dashboard is part of a developer's own work: there is no operation that lists keyspaces, only `apis.getApi` by ID; a keyspace's name, default prefix and delete protection change only on its settings page ("There's no API for this"); rate limit namespaces are renamed and deleted only in the dashboard; Compute "Resource metrics are only in the dashboard", including the instance events that explain an `OOMKilled` or `CrashLoopBackOff` restart; and the audit log, which every workspace role reads, has no read endpoint. Root keys, once dashboard-only, now have `rootKeys.*` endpoints, and are administration in any case. Clauses 5, 6 and 7 are met by per-resource root key permissions, the published OpenAPI document and `llms.txt`, and named root keys recorded as the actor in the audit log. **Would qualify with** keyspace listing and settings, namespace management, resource metrics and instance events, and audit log reads in the API or MCP server.
- [Vitally](https://www.vitally.io) - Fails clause 2. Customer success platform. An agent given a team member's access reaches it through the first-party MCP server at `mcp.vitally.io/mcp/v0`, which acts as that person over OAuth and respects their permissions and Access Groups. It searches accounts, organizations, users, meetings, conversations, notes, docs, tasks, projects, goals, indicators, NPS responses, surveys, custom objects and segments, but it writes only by creating notes, tasks and custom object records, and nothing it holds can be updated or deleted. The REST API reaches further, with create, update and delete for organizations, accounts, users, conversations, notes, tasks, NPS responses, meetings and custom object instances, and projects created from a template, but its keys are issued under Manage Integrations, which only admins hold, so it is not a user's own path. Even with it, nothing creates or edits a Doc, sets a Goal, addresses an Indicator, enrols an account in a playbook or sends an email: the Conversations reference says its endpoints "do not start conversations with participants or send outbound messages", and an account's segments are editable "In-app". Clause 4 is met by the web app, clause 5 by the MCP server enforcing each user's permissions, and clause 6 by `docs.vitally.io/llms.txt` and protected-resource metadata at `mcp.vitally.io/.well-known/oauth-protected-resource/mcp/v0`. Clause 7 is not met as documented: REST keys are named, revocable workspace keys with no documented scopes whose records name whichever admin the caller passes, and the MCP server attributes everything to the signed-in person with "no built-in marker". **Would qualify with** MCP tools that update and delete what a user works on, plus machine-callable writes for Docs, Goals and Indicators, sending a conversation and enrolling in a playbook.
- [Beads](https://github.com/gastownhall/beads) - Fails clause 4. Ticketing is squarely in scope and it passes clause 2, because issue types come from `.beads/config.yaml` and an operator runs the whole product from the CLI. But it ships no human interface: `bd human` is a subset of the same CLI that serves as its machine interface, `bd serve` is "the beads HTTP API over loopback", and every graphical UI is community-built. Counting one CLI as both interfaces would make clause 4 self-satisfying. **Would qualify with** a shipped human surface.

## Eligible, pending evidence

These meet the clauses on everything the published material settles, and turn on one question it leaves open. They are neither listed nor ruled out until someone answers it, with a link to the documentation page, the generated schema or the runtime metadata that does, or with a round trip where nothing published will.

- [AnyDB](https://www.anydb.com) - Turns on views. Business records and operations platform whose hosted MCP server at `mcp.anydb.com` reaches the everyday work: records, bulk edits, copies and moves, assignments and the Inbox, keyword and semantic search, comments, files, record and form shares, saved reports, and workflows including those behind button cells, with RFC 9728 and RFC 8414 metadata and an OpenAPI document at `/openapi/spec.yaml` for clause 6. Groups and role assignment remain interface-only, which is administration and so good practice. The open question is views. A person's saved view is a named filter tab on a type's listing page, "saved globally and available for all users", and the published MCP reference says "MCP View tools do not read or write those tabs", while the current source of the vendor's `anydb-mcp-service` defines `anydb_create_view` as creating "a View on a type's listing page" and adds record-version, revert and document-generation tools the reference does not list. **Would be listed with** a `tools/list` against the hosted server, or a round trip that creates a listing-page view.
- [Hanko](https://www.hanko.io) - Turns on whether a Hanko Cloud member's console work all maps onto the admin API. Authentication and user management system. The admin API at `docs.hanko.io/openapi-admin.yaml` creates, updates and deletes users, emails, passwords, passkeys, OTP, sessions and metadata, manages webhooks, organizations and their members, roles and role bindings, and lists audit logs, though on Cloud it is limited to the Pro and Enterprise plans and `GET /users` filters by id and email only. Bulk import is console-only, and so are settings such as social and enterprise SAML connections, sessions and email delivery, which are administration and so good practice, unless adding an enterprise connection for each customer is ruled recurring user work. Self-hosted, the distribution ships login and profile components and no administration interface, so only Cloud meets clause 4. Clause 3 is met thinly by the admin API reference and a generated skill at `docs.hanko.io/skill.md`, and clause 6 by `docs.hanko.io/llms.txt`, an agent-skills index and the OpenAPI document. **Would be listed with** a round trip on Hanko Cloud showing the console's Users page holds no work the admin API lacks.
- [Typebot](https://typebot.com) - Turns on whether an agent can author a working flow from what is published. Visual builder for chatbots on websites and in messaging apps. The builder OpenAPI document at `docs.typebot.com/openapi/builder.json` covers a builder's week: typebots are created, imported, fetched and patched as whole documents of groups, blocks, edges and variables, published and unpublished, results are read, deleted and transcribed, analytics and folders are reachable, and the viewer API starts, continues and previews chats. Inviting members and storing integration credentials are not in the published reference, which is administration and so good practice. What is unsettled is clause 3: only a handful of operations carry descriptions, there is no MCP server or agent guide, and the flow document is learnable only from the schema and the per-block editor docs. Clauses 4, 5 and 6 are met by the builder, write checks in `handleUpdateTypebot.ts`, and the OpenAPI documents with `docs.typebot.com/llms.txt`. **Would be listed with** a round trip in which an agent builds and publishes a working flow from the schema and block docs alone.

## Fails the quality bar

This meets enough of the definition to be worth re-checking. It fails on licence and maintenance, which are the easiest things on this page to fix.

- [cluster-software/agent-crm](https://github.com/cluster-software/agent-crm) - No licence file, and the public repository is now a legacy pointer: its README says new code and releases come from an Agent CRM monorepo that is not public, and its last commit was on 2026-06-05. The npm packages `@agent-crm/cli` and `@agent-crm/sdk` declare no licence either, and getcluster.ai now describes an outbound sales workspace without mentioning Agent CRM. **Would qualify with** a licensed public repository, or public product documentation if it is sold commercially, and then an assessment against the clauses.
