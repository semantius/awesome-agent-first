# Considered, not listed

Every candidate assessed for this list that did not end up in the readme, why, and what would change that. Checked 2026-09-22, with the entries below dated 2026-09-23 added on that date.

This file exists because an inclusion rule nobody can see being applied is just a claim. Nothing here is a criticism of the software. Several of these are better built and more widely used than entries that did qualify, and a few fail on something as small as a missing licence file. "Not listed yet" is meant literally: say so in an issue when one of these changes and it gets re-checked.

The criteria are in [contributing.md](contributing.md). Software that fails clause 4 by design is recorded separately in [agent-only.md](agent-only.md), because being built agent-only is a decision rather than a shortfall.

**Corrections are welcome and will be made quickly.** Every claim here was checked against the project's own repository, documentation or a live response on the date given, and is a snapshot of what was public then. That method is fallible in three ways: a capability can exist somewhere the check did not look, undocumented behaviour is invisible to it, and everything here goes stale as projects ship. If something is wrong about your project, open an issue or a pull request with a link to what shows otherwise. Factual corrections are not argued with. Judgement calls, meaning whether a clause is the right clause, are worth discussing in the open, and that discussion belongs in an issue where everyone can read it.

## Fails a clause

- [agent-desk](https://github.com/huabeitech/agent-desk) - Fails clauses 2 and 3. The MCP server it ships at `/api/mcp` registers two tools, `server_time` and `service_info`, and `internal/ai/mcps/registry.go` leaves a comment where further providers would go; the working MCP integration is the client that lets its own AI agent call external tools, which is the consumer direction rather than a way in. The dashboard's HTTP surface does reach roles, permissions, tickets and knowledge bases, but nothing documents it: the documentation site has no API reference, `llms.txt` and `.well-known/mcp.json` both return 404, and the "Open API" in the channel settings is OpenIM, a chat channel. Authorization is enforced server-side, which satisfies clause 5, but authentication is a password login issuing a session token, with no credential an agent could hold. **Would qualify with** an OpenAPI document over the dashboard routes and MCP tool providers covering tickets, conversations and knowledge.
- [Relaticle](https://github.com/relaticle/relaticle) - Fails clause 2. Custom field definitions are read-only everywhere they are reachable: the MCP server offers `list-custom-fields-tool` and `get-crm-schema-tool` with no write equivalent, `CustomFieldsController` implements only `index`, and no console command defines one. Creating a custom field requires the Filament admin panel, and defining fields is something an operator has to do, so clause 2 fails. Re-read 2026-09-23 under the operator wording: the verdict is unchanged, because no shell path exists for a reference agent to take either. **Would qualify with** a writable custom-fields endpoint or MCP tool.
- [Agentic Postgres](https://www.tigerdata.com/blog/postgres-for-agents) - Fails clause 4 under the audience test. Its human paths are psql, third-party SQL clients and the console SQL editor, which are database administration tools rather than interfaces for the people whose records live there. **Would qualify with** a shipped interface for working with the data as records.
- [Airtable](https://airtable.com) - Fails clause 2. Checked 2026-09-23. The access half is not where it falls short. SCIM 2.0 creates, patches and deletes users and groups, `Update collaborator base permission` and `Update workspace collaborator` move a person or a group to a level narrower than full, and the permission levels themselves are a fixed set nobody extends, so that much is parity rather than a gap, though both of those writes are marked "Billing plans: Enterprise (pre-2023.08 legacy plan), Enterprise Scale" and below that tier the grant is something only the interface does. Clause 6 is met twice over, by an llms.txt tree at `airtable.com/developers/llms.txt` whose first section is addressed to agent integrations, and by RFC 9728 protected-resource metadata at `mcp.airtable.com` advertising `schema.bases:write` among its scopes. What the machine interface does not reach is the schema it holds that scope over. Fields are created at `POST /v0/meta/bases/{baseId}/tables/{tableId}/fields` and nothing deletes one, nor deletes a table, while bases, workspaces and views all have deletes. Update field "updates the name, description, and/or options of a field", so the type conversion the interface performs from a menu has no API form. Views can be read and deleted but not created, and their filters, sorts and grouping are configurable nowhere but the interface. Because that llms.txt indexes every endpoint Airtable publishes, the absences are a finding rather than an argument from silence. Re-read 2026-09-23 under the operator wording, and they survive it: retyping a field and building the view a team works in are things an operator does to run a base, not presentation settings, and below the Enterprise tier granting access is a click as well. The first-party MCP server at `mcp.airtable.com` is a real way in, creating bases, records, automation drafts and interface pages, but it does not close the schema gap. **Would qualify with** field and table deletion, field type conversion, and view creation.
- [AnyDB](https://www.anydb.com) - Fails clause 2. Checked 2026-09-23. Business database platform whose hosted MCP server at `mcp.anydb.com` is a way in rather than a read path: 56 tools, of which `anydb_create_type` and `anydb_update_type` define types, fields, layout, title formulas and child policy and migrate existing records, while `anydb_get_type_definition` and `anydb_discover_types` read the model back and the server publishes its permission guide and a machine-readable authoring schema as MCP resources. Discovery settles clause 6 several times over: RFC 9728 protected-resource metadata naming the scopes `mcp:read`, `mcp:write` and `mcp:author`, RFC 8414 authorization-server metadata with dynamic client registration, PAR, DPoP and a revocation endpoint, and an OpenAPI document served at `/openapi/spec.yaml`. What the machine interface does not reach is the access model. `anydb_get_permissions` and `anydb_check_permissions` only read, `anydb_list_team_groups` only lists, neither the OpenAPI document nor the TypeScript SDK adds a write, and the admin documentation puts group creation behind the Manage Team panel and role assignment behind the Team Properties panel. Roles themselves are built-in for everyone, which is no gap at all, but a team group and the permissions hanging off it are things only the interface creates. Re-read 2026-09-23 under the operator wording: granting access to what it has just built is one of the three things an operator must do, so the verdict is unchanged. `anydb_create_share` does grant a group view-only access to a single record, which is narrower than full access, but a per-record share is not a role assignment. Clause 4 is comfortably met by the web app. **Would qualify with** tools that create team groups and assign roles or permissions.
- [AnythingLLM](https://anythingllm.com) - Fails clause 1. Checked 2026-09-23. The machine half is stronger than the product's framing suggests, and none of it is where it falls short. `server/swagger/openapi.json` publishes 60 paths under the title AnythingLLM Developer API, "endpoints that enable programmatic reading, writing, and updating of your AnythingLLM instance": workspaces and threads, documents and folders, embeds, users, invites and instance preferences, with `POST /v1/workspace/{slug}/vector-search` for retrieval and `GET /v1/document/metadata-schema` returning "the known available metadata schema" and the acceptable type of each key at runtime. Roles are the fixed set of default, manager and admin, which is parity rather than a gap, and the per-resource grant the round trip weighs most heavily is reachable through `POST /v1/admin/workspaces/{workspaceSlug}/manage-users`, which sets a workspace to be accessible by the given user ids. Every admin path does carry the sentence "Methods are disabled until multi user mode is enabled via the UI", but that describes where a person does it rather than a restriction on who may: `server/utils/middleware/validatedRequest.js` calls `next()` outright while the instance is in single-user mode and `AUTH_TOKEN` or `JWT_SECRET` are unset, so on a fresh instance an agent can `POST /api/system/enable-multi-user` itself and unlock the rest, which is a bootstrap step rather than an asymmetry under [contributing.md](contributing.md#verifying-clauses-2-and-3). What it cannot do is find that endpoint, which the published document omits, the same weakness as `update-env` telling a caller to "refer to codebase" for its keys, and that is a clause 3 finding about discovery rather than a clause 2 finding about capability. Clause 1 is what rules it out. The product is the assistant: custom agent skills, agent flows, and an MCP integration that is a client reading `anythingllm_mcp_servers.json` to call external servers, which is the consumer direction rather than a way in. The workspace store underneath is the memory-store category the readme's Related Lists already serve. **Would be reconsidered if** the knowledge store became a governed way in of its own, such as a first-party MCP server over its own workspaces under the same permission model.
- [Attio](https://attio.com) - Fails clause 2. Checked 2026-09-23. The schema half is strong, and the identity plane is the cleanest example on this page: `POST /v2/objects` creates a custom object, `POST /v2/{target}/{identifier}/attributes` adds fields across the documented attribute types with select options and statuses beside them, and SCIM 2.0 sits inside the same OAuth-scoped API rather than off to one side, with `Create a SCIM user` taking an `appRole` of `admin` or `member`, `Create a SCIM group` building the team, and `List SCIM schemas` describing both, all under `user_management:read-write`. That is the identity plane delegated the way [contributing.md](contributing.md#verifying-clauses-2-and-3) says it may be, by a product that implements the protocol itself. Clause 3 is settled by `POST /v2/objects/records/search` across objects, granular filters on the query endpoints, and attribute definitions carrying titles, types and options; clause 6 by an OpenAPI document at `api.attio.com/openapi/api`, an llms.txt indexing every documentation page as markdown, and a first-party MCP server at `mcp.attio.com/mcp` behind OAuth whose `update-list` tool changes a list's permissions. The authorization plane is where it stops. Objects carry permissions in the product: the help centre's Manage access to objects documents a Permissions tab granting the workspace, teams, individual members and automations one of full access, read and write, or read only. The `object` schema in the OpenAPI document carries `api_slug`, `singular_noun`, `plural_noun` and `created_at`, and nothing in that document reaches object permissions, so an agent that has just created a custom object cannot then say who may see it. Re-read 2026-09-23 under the operator wording, and that is the operation to name: setting who may see an object it has just defined. Everything else an operator needs is reachable. `PATCH /v2/lists/{list}` does grant on a single resource, through `workspace_access` and a `workspace_member_access` array at three levels, but its entries carry `workspace_member_id` only, so a team SCIM has just created is a grouping nothing can be granted to. Workflows, dashboards and saved views have no endpoints either, and views are listable without being creatable. Clauses 4, 5 and 7 are comfortable. **Would qualify with** object permission endpoints and team grantees on list and object access.
- [Documenso](https://documenso.com) - Fails clause 2. Checked 2026-09-23. The signing half is fully machine-callable: the v2 OpenAPI document at `app.documenso.com/api/v2/openapi.json` publishes 89 paths over envelopes, documents, templates, fields, recipients, attachments and folders, `envelope-find` takes a `query` search parameter alongside filters on type, template and status, and audit logs and completion certificates download per envelope. What that document does not contain is anything for organizations, teams, members, roles, webhooks or API tokens, all of which the web app has, and its thirteen tags are the whole of the surface, so an agent can create an envelope and cannot say who on the team may see it. A reference that indexes every path it serves makes the absence a finding rather than an argument from silence. Clause 6 is met by that document, and team-scoped tokens carry clause 5. **Would qualify with** organization, team and member endpoints, and webhook and token management beside them.
- [Formbricks](https://formbricks.com) - Fails clause 2. Checked 2026-09-23. The management API creates and updates surveys, which is the model an agent would want to define, and covers responses, action classes, webhooks and contacts. Two things stop there. Contact attribute keys, the closest thing the product has to user-defined fields, are readable and nothing creates one, since the API reference lists get-all and get-by-id with no POST beside them. And the access model has no machine form at all, with organizations, teams, project roles and workspace permissions documented as user-management screens, so an agent that has just built a survey cannot say which team may work on it. Clause 7 is weak for the same reason, because the documentation describes a personal API key that "gives you full access to all data and settings available in your Formbricks account" rather than a credential scoped to what an agent needs. **Would qualify with** endpoints for teams, project roles and contact attribute key creation.
- [monday.com](https://monday.com) - Fails clause 2, and as narrowly as anything on this page. Checked 2026-09-23. The platform API defines the model rather than only filling it: `create_column` with type-specific settings, `change_column_metadata` for a column's title and description, `delete_column`, `create_board`, `create_workspace`, `create_folder`, and table views creatable and updatable through the Platform MCP, with `get_column_type_schema` describing each column type at runtime on top of GraphQL introspection. The per-resource grant is covered end to end: `create_team` and `add_users_to_team` build the grouping, `add_teams_to_board` and `update_teams_board_role` attach it to a board at a chosen role, `set_board_permission` sets the board default, and `update_users_role` assigns an account role. Clause 6 is comfortable, with an llms.txt indexing every documentation page in markdown alongside OpenAPI, and so is clause 7, with a hosted MCP server at `mcp.monday.com/mcp` behind OAuth 2.1, protected-resource metadata and dynamic client registration. One thing the admin interface defines that the API does not: on the plans offering custom account roles an admin creates them by clicking, and the `account_roles` reference carries a query with no mutation beside it. That is an absence rather than a refusal, because the authentication documentation states that "personal tokens have all permission scopes", so an account admin's own credential meets the same wall as anyone's. Re-read 2026-09-23 under the operator wording, which supplies the threshold the earlier reading lacked. It still fails, and the operation to name is defining a custom account role: on the plans that offer them, an operator who needs one has no way to make it but to click. It is the narrowest finding on this page, because every per-resource grant is reachable and only the account-level vocabulary is not. **Would qualify with** a mutation that defines a custom account role.
- [Notion](https://www.notion.com) - Fails clause 2. Checked 2026-09-23. The Developer Platform that launched on 13 May 2026 closed most of the distance: the `ntn` CLI is generally available on every plan, Workers run first-party TypeScript in Notion's own sandbox, and the hosted MCP server reaches further than the REST API does, with `notion-create-database`, `notion-update-data-source` and `notion-create-view` defining the model and `notion-query-data-sources` accepting SQL over it. Clause 3 is comfortable, since `Retrieve a data source` returns every property's name, type and description, and search comes in two forms, keyword through `notion-search` and semantic through `notion-ai-search` across Notion and connected sources. Clause 6 is met four times over, by OpenAPI documents at `/openapi.json` and `/openapi-adminApi.json`, an `llms.txt` indexing every reference page as markdown, the MCP server itself, and an Agent Skills API at `/v1/ai/skills/{id}`. Clause 7 is met by personal access tokens and OAuth tokens carrying introspection, refresh and revocation, with `List personal access tokens in a workspace` and `Revoke a personal access token in a workspace` letting an administrator end an agent's credential without touching anyone's session. What no surface reaches is the authorization plane. The main API publishes 48 paths and the Admin API 32, and between them nothing sets a permission level on a page, database, data source or teamspace. The Admin API builds groups at `/v1/spaces/{space_id}/groups` and fills them at `.../members`, which is the identity plane [contributing.md](contributing.md#verifying-clauses-2-and-3) says may be delegated, while `/v1/spaces/{space_id}/agents/{agent_id}/permissions` grants sharing on a Custom Agent and has no equivalent for content. The CLI documents no share or permissions command, and Notion's own MCP tool reference records that no tools for managing permissions, sharing settings or granular access control exist. An agent can therefore create a database, add properties across several types and fill it, and then cannot say who may see it, so sharing is a step only the interface can take, and granting access is one of the three things clause 2 names an operator as having to do. Because both OpenAPI documents index every path Notion serves, the absence is a finding rather than an argument from silence, and it is a gap rather than a refusal, since an organization bot token carrying every admin scope meets the same wall as a personal one. **Would qualify with** an endpoint that grants a person, group or teamspace a permission level on a page or database.
- [OpenStatus](https://www.openstatus.dev) - Fails clause 3. Checked 2026-09-23. Configuration is not where it falls short: the v2 API at `api.openstatus.dev/openapi.json` creates HTTP, TCP, DNS, ICMP and gRPC monitors, status pages with their components and component groups, status reports, maintenance windows, notification channels and private locations, which is most of what the dashboard does. Reading is. `ListMonitors` takes no parameters at all, and the other list operations are the same shape, so there is no granular filtering and no search over the model, which is the second half of clause 3 rather than a detail of it. Workspace members, their roles and API keys have no endpoints either, so the grant the round trip weighs most heavily is a dashboard act. Clause 6 is comfortably met by the published document, and clause 4 by the web app and the public status pages. **Would qualify with** filters and search on the list operations, and workspace member endpoints.
- [Recall](https://www.recall.it) - Fails clause 2. Checked 2026-09-23. Formerly getrecall.ai, and the clearest read-only case on this page, because both machine surfaces say so in their own words. The API is three endpoints, `GET /api/v1/cards`, `GET /api/v1/cards/{card_id}` and `GET /api/v1/search`, under the line "The API currently supports read-only operations. A write API is on the roadmap, stay tuned." The hosted MCP server at `backend.getrecall.ai/mcp/` is four tools, `search`, `filter_by_metadata`, `get_document_content` and `explore_kb`, under "The MCP server currently provides read-only access to your knowledge base. Write capabilities are coming soon", and the single scope it asks for is `kb:read`. Meanwhile the web app is where a person creates cards, edits the text the model generated, retags it and links one card to another, so an operator cannot put anything into the knowledge base at all without the web app, which is the whole of the product. Nothing else here is weak: filtering is granular, semantic search covers the whole knowledge base rather than one endpoint per screen, clause 4 is comfortably met by the web app and the browser extension, and clause 7 is met twice, by OAuth authorization in the browser with no key to copy and by `sk_` keys carrying expiries from 30 days to never, ten active per account. **Would qualify with** the write API and the MCP writes already on its roadmap.
- [SmartSuite](https://www.smartsuite.com) - Fails clause 2. Checked 2026-09-23. The schema half holds up: the REST API creates solutions and tables, adds fields singly and in bulk, updates and deletes them, and creates views, so an agent can build the model it is about to work against. Roles are the fixed set of Admin, Solution Manager, General, System and Guest, which is no gap in itself, since [contributing.md](contributing.md#verifying-clauses-2-and-3) says that where the roles are a fixed set, assigning an existing one is the whole of the test. What has no machine form is the assigning, nor the grant beneath it. Org Management documents six pages, the member object, list members, update member, the team object, list teams and add team, and nothing beside them: no endpoint reaches solution, table or field permissions, which the help centre puts in the Manage Solution Permissions dialog, and the update-member page does not say that `role` is writable. An agent can therefore create a table and cannot say who may see it. Re-read 2026-09-23 under the operator wording: granting access is one of the three things an operator must do, and neither half of it has a machine form here, so the verdict is unchanged. Six pages is a thin section to argue from silence over, so this is the entry here most likely to be wrong. A link to a permissions endpoint would settle it, and under the round-trip rule in [contributing.md](contributing.md#verifying-clauses-2-and-3) this is the entry on this page where running it would settle more than further reading. Clause 6 has nothing to point at either, since `developers.smartsuite.com/llms.txt` returns the documentation site's own shell rather than an index, no OpenAPI document is published, and the MCP server in circulation is SmartSuiteFoundry's rather than SmartSuite's, which makes it a connector under the scope rules. Clause 7 fails as well, because an API key is a user's key carrying "the same permissions as the user generating the key", so the documented pattern is spending a seat on an API member account rather than issuing an agent a credential of its own, leaving clause 5 to carry the one-of requirement. **Would qualify with** endpoints for solution or table permissions and documented role assignment.
- [Tailor](https://www.tailor.tech) - Fails clause 4. Checked 2026-09-23. Headless ERP that markets itself as "designed for humans and AI agents alike", and the machine half holds up: TailorDB types, fields and per-operation permissions are declared in the first-party TypeScript SDK and applied with `tailorctl`, which is a shipped command an agent runs itself, and the GraphQL API is generated from that schema. What it does not ship is an interface for the people whose records these are. The Console manages the workspace and inspects deployed resources, the GraphQL Playground is a developer tool, and the operational frontend is something you build. AppShell, the current framework, calls itself an "opinionated React application framework for creating applications on Tailor Platform", and its documentation has developers declare modules and resources in TypeScript and supply their own page components. The platform page lists "Generate UI from Schema" as coming soon, and offers out-of-the-box applications to customize "whether you build them yourself or we build it for you". That is clause 4's "reaching your own data should not require building a client first", judged against finance and operations staff rather than developers. **Would qualify with** a shipped operational interface for working with the records.
- [Trigger.dev](https://trigger.dev) - Fails clause 1 under the scope rules in [contributing.md](contributing.md#not-on-this-list). Checked 2026-09-23, re-read 2026-09-23. **The earlier reason has been withdrawn.** This was recorded as failing clause 2 because reaching a new task means `trigger.dev deploy` building and redeploying a worker. Clause 2 now asks whether an operator can run the software with only an agent, assessed against an agent that runs repository workflows, and no admin interface defines a task either: the dashboard shows runs, traces, schedules and environment variables and authors nothing, so there is no operation here that only a person can reach. The machine half is broad, with 51 paths in the published OpenAPI document covering runs and their traces, schedules, environment variables, queues and concurrency, deployments, batches, bulk actions and waitpoint tokens, plus `/api/v1/query` and `/api/v1/query/schema`, which describe what is queryable at runtime. What rules it out is scope. It describes itself as a way to "build and run durable AI agents and workflows in TypeScript", which is the orchestrator side covered by the readme's Related Lists rather than software holding an organization's records. **Would be reconsidered if** the case is made that a durable execution platform is the producer side rather than the consumer side, which is a judgement about the scope rules rather than about the clauses.
- [Typebot](https://typebot.io) - Fails clause 2. Checked 2026-09-23. The builder API is better than most visual products manage: 35 documented operations create, import, update, publish and unpublish typebots, so the flow a person draws is a document an agent can write, and folders, workspaces and results are all reachable. Membership is where it stops. `List members` is the only member operation in the reference, while the documentation has a person add members and guests in the workspace screen, so an agent can build a bot and cannot give anyone access to it. Clause 6 is met by the builder OpenAPI document at `/openapi/builder.json`. **Would qualify with** endpoints that invite a member and set their role.
- [Unkey](https://unkey.com) - Fails clause 2, narrowly. Checked 2026-09-23. The authorization plane is exactly what this list asks for: `permissions.createPermission`, `permissions.createRole` and `permissions.setRolePermissions` define the vocabulary, `keys.addRoles` and `keys.setPermissions` attach it to a credential, and identities, API namespaces, ratelimit overrides, projects, deployments, domains, environment variables and gateway policies sit in the same v2 surface, so the deploy product is as machine-callable as the key product. Two things the dashboard does are not in that specification. Root keys, the credentials that reach all of it, are created, rotated and deleted under Settings with no endpoint beside them, which is more than the one-time bootstrap the criteria excuse once an agent needs a narrower key for another agent. And the audit log, which the documentation presents as the record of every change to keys and configuration, is readable in the dashboard and nowhere in the API. Clause 6 is met by the published OpenAPI document and clause 7 by workspace root keys carrying their own permissions. **Would qualify with** root key creation and audit log reads in the API.
- [Beads](https://github.com/gastownhall/beads) - Fails clause 4. Ticketing is squarely in scope and it passes clause 2, because issue types come from `.beads/config.yaml` and an operator runs the whole product from the CLI. But it ships no human interface: `bd human` is a subset of the same CLI that serves as its machine interface, `bd serve` is "the beads HTTP API over loopback", and every graphical UI is community-built. Counting one CLI as both interfaces would make clause 4 self-satisfying. **Would qualify with** a shipped human surface.
- [OpenChatCut](https://github.com/0xsline/OpenChatCut) - Meets clauses 1 to 4 but fails the requirement to meet at least one of clauses 5, 6 and 7. It is explicitly single-user and local, so there is no authorization model to enforce, its agent credential is a static bearer token rather than a scoped identity, and its skills index sits in `~/.openchatcut/skills/` rather than being published. **Would qualify with** a multi-user permission model or per-agent credentials.

## Eligible, pending evidence

These meet the clauses on everything the published material settles, and turn on one question it leaves open. They are neither listed nor ruled out until someone answers it, with a link to the documentation page, the generated schema or the runtime metadata that does, or with a round trip where nothing published will.

- [ERPNext](https://erpnext.com) and the [Frappe Framework](https://frappeframework.com) underneath it - Checked 2026-09-23. Frappe generates a REST API for every DocType and the Desk interface is a client of that same API, which is a strong clause 2 story, and role permissions and user permissions are enforced server-side for clause 5. The open question is whether an agent can create a DocType, and therefore the model itself, through the API. `DocType` is a DocType, so `POST /api/resource/DocType` ought to work, but neither the REST API reference nor the Manipulating Documents guide documents schema creation or any metadata endpoint, and both cover document instances only. Note also that every Frappe MCP server found was third party, so they are connectors under the scope rules, and OpenAPI generation is likewise a third-party app rather than something Frappe publishes about itself. **Would be settled by** the metadata a running instance serves for `DocType` itself, which would count under the runtime-discovery rule in [contributing.md](contributing.md#verifying-clauses-2-and-3) even though the reference omits it, or failing that a round trip creating a DocType, adding fields, creating a Role and a narrowed Custom DocPerm, and operating against them.
- [Palantir Foundry Ontology](https://www.palantir.com/docs/foundry/ontology/overview) - Checked 2026-09-23, re-read 2026-09-23. **The earlier reason has been withdrawn.** This was recorded as failing clause 2 on the grounds that ontology-as-code through SuperRepos is "a repository workflow a person deploys, not an interface an agent calls". A repository workflow is something the reference agent in [contributing.md](contributing.md#gate-one-the-definition) runs itself, so that reasoning no longer holds, and it was refutable from Palantir's own documentation in any case. The path that would qualify is SuperRepo, where object types, links, interfaces and actions are declared in TypeScript and applied with a deploy command rather than through Ontology Manager. Two things are unsettled. The SuperRepo mechanism has not been verified here against Palantir's documentation, only reported, and nothing in this file should rest on a report. And SuperRepo is documented as being in beta and as possibly unavailable on a given enrollment, so whether a reader can reach the path at all is unknown. Maturity is not a criterion on this list and beta software is listed elsewhere on it; reachability is what is open. Note that the platform API reads the ontology without defining it, so without SuperRepo the entry fails clause 2 on the original ground. **Would be settled by** the SuperRepo documentation pages behind the declaration and deploy steps, and confirmation that the path is reachable on a standard enrollment.
- [Strapi](https://strapi.io) - Checked 2026-09-23, re-read 2026-09-23. **The earlier reason has been withdrawn.** This was recorded as failing clause 2 because the Content-Type Builder "is only accessible to create and update content-types when your Strapi application is in a development environment, else it will be in a read-only mode in other environments", so a running production instance cannot define content types. That is symmetric: in production the builder is read-only for a person too, and no operation there is reserved to clicking. Content types are schema files in the repository, and an agent with a shell writes them and deploys, which counts under the reference agent in [contributing.md](contributing.md#gate-one-the-definition). The open question is the half that was never assessed. Granting access is one of the three things an operator must do, and nothing checked so far shows whether the Users and Permissions roles and their per-content-type permissions are reachable without the admin panel. **Would be settled by** a documented endpoint or command that creates a role and sets its permissions on a content type, or a round trip that defines a content type, deploys it to a running instance, grants a narrowed role and operates against it.

## Fails the quality bar

Each of these meets enough of the definition to be worth re-checking. All four fail on licence or maintenance, which are the easiest things on this page to fix.

- [cluster-software/agent-crm](https://github.com/cluster-software/agent-crm) - No licence detected, last push 2026-06-05. The most adopted of the unlicensed candidates at 118 stars. **Would qualify with** a licence file.
- [keshav55/agent-crm](https://github.com/keshav55/agent-crm) - No licence detected, last push 2026-08-28, so actively worked on. **Would qualify with** a licence file.
- [agentsfirst](https://github.com/capitalthought/agentsfirst) - No licence detected on the repository, last push 2026-06-16. The framework it documents is still cited under Assessment and Reading, because reference material is not held to the software gates.
- [pg-mcp-server](https://github.com/stuzero/pg-mcp-server) - Last push 2025-09-10, beyond the six-month line, and a connector over PostgreSQL rather than a product.

## Out of scope

- [BigQuery](https://cloud.google.com/bigquery) - Meets the clauses and is excluded on curation. What makes it eligible, DDL, `GRANT` and `REVOKE`, row access policies and `INFORMATION_SCHEMA`, is equally true of Snowflake, Databricks, Redshift, ClickHouse and PostgreSQL itself, so admitting it admits every cloud database. Its agent-specific capability, BigQuery Graph, was in preview when this was checked. **Would qualify with** generally available capability built for agents rather than generic administrability.
- [Bonnard](https://bonnard.ai) - The agentic semantic layer assessed here was archived on 2026-07-03, and its repository now points to a different current product. That product, `@bonnard/mcp-charts`, is an SDK that "adds interactive charts to any MCP server". It fails clause 1: a library a developer embeds in their own server, which neither holds nor governs data of its own.
- [DuploCloud AI Help Desk](https://duplocloud.com/blog/ai-help-desk-for-devops/) - Fails clause 1. The product is the agents: AI DevOps Engineers specialized in Kubernetes, observability, compliance and cost, with the help desk as the queue people file requests into. The platform underneath, Automation Studio with `duploctl` and a first-party MCP server, is a separate candidate, and it provisions cloud infrastructure rather than holding an organization's records. The centralized MCP server fronting Kubernetes, cloud providers, OpenTelemetry and CI/CD is a connector over someone else's system.
- **Activepieces OSS Friends, screened rather than assessed** - Checked 2026-09-23. The rest of that list was screened and stopped at the scope rules rather than at a clause. Agent frameworks, gateways and observability: VoltAgent builds the consumer, and Bifrost, Portkey AI and Langfuse are the model-gateway and LLM-observability categories the readme's Related Lists already serve.
